# Developer 3 integration runbook

Branch: `feat/ai-matching`. All existing backend routes and DTO schemas are unchanged. The only shared runtime edit is importing and mounting the owned router in `app/main.py`; `openapi.json` was regenerated by the backend's export script. No migrations, repository rewrites, backend answer-service edits or frontend changes are included.

## Configure and verify

From `services/api`, use the backend `.env.example` for database/CORS settings, then append the server-only variables in `app/modules/ai/.env.example`. Choose a Gemini model enabled for your project with structured JSON support. No default model is assumed. Restart after changing settings. The REST schema format follows [Google's Generate Content structured-output guide](https://ai.google.dev/gemini-api/docs/generate-content/structured-output).

```bash
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/mypy app tests
.venv/bin/pytest --cov=app.modules --cov-report=term-missing
.venv/bin/uvicorn app.main:app --reload
```

Extraction has a 1000-character input limit, 64000-byte response cap, 2048 output-token limit, 10-second socket timeout and global 20-calls/minute budget per process. The socket timeout is not a total wall-clock deadline. Use shared rate limiting before multiple workers. No new runtime dependency is required. No keys, utterances, model responses, source excerpts or direct identifiers are persisted by these modules. Identity/banking text is refused before the model call; pattern checks are not a general-purpose PII detector. Current extraction supports en-IN; other locales use manual entry.

## Frontend contract handoff

1. Create the existing anonymous profile session (`POST /api/v1/profiles/sessions`).
2. Call `POST /api/v1/profiles/extract` with text and locale. Output always has `needs_review: true`. It is stateless and cannot overwrite a confirmed answer. A 503 or 429 explicitly offers manual entry; matching needs no Gemini key.
3. Show all draft facts for human review/correction. Submit only the reviewed profile in `POST /api/v1/matches` (`session_id`, `facts`, optional `limit`). This submission confirms non-null values. Omitted fields retain previous answers. Null newly supplied fields stay unprovided, so follow-ups still work; null clears a previously confirmed field.
4. Show the existing verdict enums and rule groups. The deterministic rule reason describes the reviewed condition, source UUID and missing fields. `all_checked_conditions_met` means only that the checked conditions passed, never approval. Relevance is a lexical ranking score, never a percentage eligible. Without candidate category/geography metadata, it uses occupation/category terms against the reviewed scheme name. Metadata enrichment requires the backend/data owner.
5. Call `POST /api/v1/questions/next` with session/run IDs. It uses reviewed rule templates, skips explicit answers, considers only recorded current public versions, and probes whether an answer can change the verdict. A profile correction makes older runs return 409; rematch first. No available question has null metadata and empty options. Multi-field rule templates need reviewed per-field mappings and are skipped rather than repurposed.
6. Submit `POST /api/v1/profiles/answers`. Land registration values are yes/no/not_sure. For boolean fields map Yes/No to true/false and Not sure to null. Numeric/text Not sure maps to null. This preserves the backend DTO and answer implementation. A stored unknown remains unknown and is not repeatedly asked.
7. Rematch with the reviewed corrected facts, or `{}` to use stored confirmed values. Only USER-origin facts enter matching. An invalid legacy confirmed value returns a redacted 422 and can be corrected through answers or matches.
8. Open the existing `GET /api/v1/guidance/{scheme_id}?session_id=...`. Guidance is entirely the backend's reviewed steps/documents/official sources, with no generated application instructions.

Every evaluated public candidate is persisted, even when the response limit hides lower-ranked items. Profile hashing and stable rule/version/source IDs make runs auditable. Negative results are grouped after possible candidates; uncertainty remains visible. Explanations always work offline from the validated candidate data; optional Gemini paraphrasing is not enabled. Source text never becomes an instruction or a rule.
